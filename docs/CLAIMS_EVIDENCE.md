# Claims and evidence

What this project can and cannot be said to do, with where to check it. Written so that a README, a resume bullet or an
interview answer can be checked against it. Status words are literal:

* **Verified**: reproduced by a test or script in this repo (path given).
* **Run once, live**: measured against the real backend and database on the date given; not re-run since.
* **Not run live**: implemented and unit tested with the database and LLMs stubbed; never executed against real data.
* **Not implemented**: do not claim it.

| Claim | Status | Evidence / what is actually true |
| :--- | :--- | :--- |
| Platform over 17M+ GDELT 2024 events | Verified (2026-10-09) | 17,480,236 events, North America only (US, CA, MX by action location). The extract rule was reproduced from the official GDELT files: 61,009 of 61,009 rows identical on a sample day (`docs/DATA_LAYER.md`). "Global" would be wrong. |
| 736 forecast series, 7-day horizon, 14-day history | Verified | 184 targets x 4 count series. `python db_scripts/eval_thp_baselines.py` reads the cached dataset: 254,656 windows, horizon 7. |
| Analyst chat answers questions with SQL statistics + ChromaDB news context + LLM | **Partly** | The chat path retrieves a top-N event sample (SQL) and an optional LLM report. It does not call ChromaDB. ChromaDB is used only in the event-report news fallback (`include_news=true`, headline missing), which the Explore UI does not enable. |
| Chat answers "did X increase this month?" | Verified live (2026-10-08) | New `compare_periods` tool counts every matching event in two complete periods and computes the change in code (`backend/services/period_compare.py`, `core_queries.query_period_counts`). Offline tests: `tests/test_period_compare.py`, `tests/test_planner_offline.py`. Live: `compare-01`/`compare-02` pass against the restored database (858 vs 1,193 Canadian protest events, February vs March 2024). |
| "Routed each query through model tiers by complexity" | **Not implemented** | Actual path: greeting and event-ID fast paths, then router extraction (Claude Sonnet 5.5 since 2026-10-09; local Qwen2.5-3B when there is no key or the call fails; regex behind that), then deterministic date and label checks, then a rule-based plan; the remote LLM plans only underspecified queries and writes reports on request. The tiers are fallbacks by availability, not by complexity; no complexity score exists. |
| Router: Claude Sonnet 5.5 with a local fallback | Verified (2026-10-09, recorded outputs) | On a 30-question set written blind by a separate agent (`tests/agent_eval_heldout_v3.json`), first run with the planner frozen: Sonnet 23/30, qwen 21/30. Sonnet's 7 failures were 5 date-parser overrides of Sonnet's correct dates and 2 scorer gaps; after fixing both, Sonnet 118/118 on all sets, qwen 116/118 (v3 is then no longer held out). On the 74 dev questions that reach the router, the rules had to override qwen's intent label 22 times and Sonnet's 0 times. `tests/eval_runs/2026-10-09_router_v3/summary.md`. |
| Custom PyTorch "Transformer-Hawkes" model | Reword | Originally a Transformer count forecaster with a Hawkes-inspired residual head (no point-process likelihood). On held-out data the head was worse in every comparison (2024 test, all 3 seeds; Q1 2025) and it was removed; the selected model is a Transformer that predicts a correction to seasonal-naive. Say "Transformer forecaster", not "Transformer-Hawkes". See `docs/FORECAST_EVALUATION.md`. |
| MAE 167.74 -> 83.77 (about 50%) | **Does not hold as stated; replaced** | 83.77 was a validation number with window leakage, selected on validation and compared with the weakest baseline. Now: retrained on 2024 plus January 2025, tested once on 2025-04-01 to 06-11: MAE 56.13 vs 62.05 for seasonal-naive (+9.5%, 3 seeds +6.1 to +15.2%), better on 67 to 72% of series; the 2024-only model got +5.7% there. Before the retrain: +5.7% on Q1 2025 and +4.9% on the 2024 held-out test. **But a LightGBM baseline on the same split did better**: +13.8% (MAE 53.52), chosen on validation and tested once; the Transformer-minus-LightGBM difference has a bootstrap 95% interval of -0.78 to +7.64, so the Transformer is not shown to beat gradient boosting. LightGBM barely moves with the seed (53.0 to 53.5 over three seeds; seed means: interval -0.42 to +7.74), and its 80% intervals by the same method cover 0.79 (0.75 for the largest series), about 8% narrower. `docs/FORECAST_EVALUATION.md`, `docs/forecast_eval/retrain_2025h1_test.json`, `docs/forecast_eval/strong_baseline_test.json`. |
| 24-question evaluation of the Planner/Executor | Verified live, before and after | `tests/agent_eval_set.json`. Before the fixes (2026-07-14): 13/24, 10 failed, 1 without a strict assertion. After (2026-10-08): 31/31, the original 24 plus 7 new items, three identical runs (`tests/eval_runs/2026-10-08_after_fixes/`). It scores tool selection and date ranges, not answer quality; the two keyword-search items returned 0 rows until the fingerprint backfill and FULLTEXT search (`docs/DATA_LAYER.md`); they now return 50 rows each. A held-out paraphrase set, run once unseen, scored 24/29 (`tests/eval_runs/2026-10-08_heldout/summary.md`): the fixes did not fully generalise, mostly because the router's intent label can disagree with the user's words. |
| Eval surfaced a high-confidence date-range error | Run once, live | `reldate-01` ("protests in Texas last week") resolved to a 131-day window with `confidence: high`; `reldate-03` to 138 days (same summary file). Root causes fixed in this branch; regression tests in `tests/test_date_utils.py` and `tests/test_planner_offline.py`. |
| Reports are grounded in the data | Verified live (2026-10-09) | 54 reports from Claude Sonnet pass five deterministic checks: every number traceable to the data (1,305 numbers), no totals, percentage trends or qualitative trends from top-N samples, comparison direction always right, no dates outside the window (`tests/eval_runs/2026-10-09_answer_quality/summary.md`). The first run had one qualitative trend claim the checks missed; the prompt and the checks were changed and it is gone. A sixth check, added later, compares counts written as words ("four records, each with 70 articles") with the records shown that have that date and article count: rechecked without new LLM calls, 3 of these 54 reports state more records than exist, so **51 of 54 pass all six** (`recheck_count_and_split.json`); across 216 saved reports it flags 7 sentences, all wrong. Rounded bounds ("more than 20,000" for 20,942) are accepted when a data value satisfies them within 10%. **Not grounded: interpretation.** On 30 of these reports, 25 contain at least one unsupported cause, motive or connection (75 of 443 sentences, labels pre-made by a Claude agent and reviewed by a person in two rounds). A Claude judge finds 91% of those sentences at precision 0.85; a keyword rule finds 60% at 0.52 (`tests/eval_runs/causal_labels/summary.md`). The report prompt was then changed (no stories, no themes, no meaning read into actor labels) and the 54 reports regenerated from the same data: the judge finds 0 unsupported sentences in the 30 (was 80), and 0 in the other 24 reports, which were not read when the prompt was written (was 26); no person has labelled the new reports, and they are drier (`tests/eval_runs/2026-10-09_report_prompt/summary.md`). After the change 52 of 54 pass the six checks (two wrong counts). Two rules were then added to the prompt (write numbers exactly; count the matching records before writing "N records"): **53 of 54 pass**, the one failure a self-contradictory count, and the judge still finds 0 unsupported sentences in all 54 (`tests/eval_runs/2026-10-09_report_numbers/summary.md`). Event-type descriptions are not checked (one was wrong). The report endpoint returned HTTP 500 for every request until a schema bug was fixed. **The checks now run on every live report**, for both report buttons: a failing one is rewritten once with what failed, then replaced by a deterministic summary; on the 216 saved reports, 8 failed and all 8 rewrites passed; three live Deep Dive reports passed, and the page shows which checks ran (`tests/eval_runs/2026-10-09_report_safety_net/summary.md`). The Deep Dive report's prompt was then given the same interpretation rules: on 15 questions the judge found 108 unsupported sentences before and 1 after, and its summary is no longer cut at 4,000 characters (`tests/eval_runs/2026-10-09_enhanced_prompt/summary.md`). |
| Month-only dates cover the whole month | Verified (fixed in this branch) | Was hard-coded to the 28th in the fast path and the 31st in the regex fallback (invalid for February and 30-day months). Now `calendar.monthrange` (`backend/queries/date_utils.py`); `TestMarchRegression`. |
| Relative dates ("yesterday", "this month") resolve sensibly | Verified (fixed in this branch) | Three different anchors existed (wall clock, 2024-01-31, none for the LLM). One anchor now: the dataset end 2024-12-31, overridable with `GDELT_REFERENCE_DATE`; the user is shown a notice. |
| Confidence label reflects correctness | **Partly, on one small set** | An evidence-based routing confidence (label overridden: low; dates re-derived from the text: medium) did not predict errors with the qwen router on v2 (high 11/13, low 7/8 passed; `tests/eval_runs/2026-10-09_heldout_v2/summary.md`). With the Sonnet router on the v3 first run it did: failures high 2/14 (both scorer gaps), medium 5/9, low 0/2; "medium" is where the date-parser bugs were. 30 questions; after the fixes there are no failures left to measure against. |
| Event-ID lookups work in natural language | Verified (fixed in this branch) | The ID pattern was anchored to the start of the input, so "tell me about event 1150442224" never reached `event_detail`. `test_event_id_in_a_sentence_goes_straight_to_event_detail`. |
| Same filters and definitions across dashboard, chat and forecast | Verified, with one documented difference | Search, comparison and the dashboard share `query_utils.EVENT_TYPE_CONDITIONS`. The forecaster uses `FORECAST_EVENT_TYPE_CONDITIONS` in both training and serving; serving used to count protest as roots 14 to 16 against root 14 in training (a train/serve skew, about 2x the input). Its conflict / cooperation are Goldstein < 0 / > 0 by design (daily volume), not the search thresholds. |
| 80% prediction intervals | Verified, close on one period | The original interval covered 1.00 of small series and 0.16 of series over 1,000 events a day. Log-space, size-binned intervals fixed the spread; with the rolling 14-day refit chosen on validation, coverage on the 2025 test period is 0.79 overall, 0.80 / 0.80 / 0.79 / 0.76 by size (the static alternative was 0.81 and even). Earlier periods: 0.73 (2024 test), 0.77 (Q1 2025). `docs/FORECAST_EVALUATION.md`. |
| MySQL indexes and precomputed summaries make queries fast | Measured for search and overview | State-year event search 12.7 s -> 0.3 s (indexed `ActionGeo_ADM1`); regional overview of a state-year 26 s -> 2.4 s end to end, including about 1 s of local routing (precomputed stats and stored daily top events). Dashboard queries not benchmarked. |
| CI/CD | Partial | `.github/workflows/tests.yml` runs the offline tests (including a replay of the eval questions on recorded router outputs: Sonnet all 118, qwen 88), the query layer against a real MySQL loaded with a slice of the data (`tests/test_db_integration.py`), and the frontend type check. The live eval through the API is run by hand. No deploy pipeline. |
